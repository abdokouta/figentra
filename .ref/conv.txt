Key decisions now locked

Actors

User
Service Account
System
Integration Actor
All go through the same IAM authorization model.

Events

Not every action becomes an event.
Meaningful business state transitions do.
Reads don't.
Commands, domain events, and audit events are separate concepts.
Transactional Outbox → durable event delivery → idempotent consumers.

Integrations / App Store

Added a proper Integration Platform.
Applications ≠ Integrations.
Tenant can install/connect/configure/pause/disconnect integrations.
OAuth/API credentials are isolated from Registry/frontend.
Feature flags only control rollout/beta availability.
Entitlements + installation + connection state determine actual availability.
Marketplace can eventually contain Applications, Integrations, Extensions and Connectors.

Versioning

Added a platform-wide @figentra/versioning.
Covers:
REST APIs
Webhooks
Events
Workflows
Integrations
SDK compatibility
Application/manifest versions
Explicit compatibility/deprecation/sunset model similar to mature platforms.

Workflows

Added @figentra/workflows.
Architecture is inspired by Medusa's Workflow SDK, particularly its workflow/step/compensation model and pluggable workflow engine. Medusa's current docs describe workflows as sequences of steps with rollback/consistency semantics and a replaceable workflow engine.
But we don't make Figentra dependent on Medusa.
Workflow ≠ event:
Workflow orchestrates work.
Event announces a completed fact.

ORM

Final decision: MikroORM, not TypeORM.
Default entity style: defineEntity + class.
Decorators remain available selectively.
MikroORM's current documentation explicitly recommends the defineEntity + class pattern and provides strong TypeScript inference.
This also fits better with the architecture we've been designing around explicit metadata/compilation.

Controllers

Not one controller per action.
Not one gigantic controller per application.
Use bounded-context/resource controllers:
ProductsController
OrdersController
CustomersController

Standard CRUD:

GET    /products
GET    /products/:id
POST   /products
PATCH  /products/:id
DELETE /products/:id

Business commands:

POST /products/:id/publish
POST /orders/:id/refund
POST /orders/:id/cancel
POST /domains/:id/verify
POST /integrations/:id/reconnect

The controller stays thin:

Controller
    ↓
Command / Query
    ↓
Use Case
    ↓
Domain
    ↓
Repository / Transaction
    ↓
Outbox
    ↓
Events

And the frontend remains exactly as we decided:

Vite
  ↓
React Router 7
  ↓
HeroUI Pro + Stackra UI
  ↓
Stackra Query
  ↓
Figentra API

No Refine, no SDUI, and no duplicate query/HTTP abstraction.

Yes. After v5, the core SaaS platform architecture is strong, but if the goal is truly Figentra as a PaaS / platform-of-platforms, there are several important capabilities still missing.

The biggest gap is that v5 describes the application/control plane very well, but not yet the complete developer/platform operations plane.

Cloudflare now gives us a lot of primitives we can exploit: Workers, Containers, Queues, Workflows, R2, KV, Durable Objects, Hyperdrive, Analytics Engine, Vectorize, etc.

One particularly important correction

Cloudflare Workflows changes our previous workflow decision.

Cloudflare now has a native durable Workflows platform with persisted state, automatic retries, long-running execution and human-in-the-loop pauses.

And Cloudflare's own guidance distinguishes:

Queues → decoupling, fan-out, buffering, batching, simple background jobs.
Workflows → multi-step durable execution where individual steps can retry independently.

So for Figentra:

Simple async
    → Cloudflare Queues

Durable multi-step orchestration
    → Cloudflare Workflows

Complex application-domain workflow API
    → @figentra/workflows
       backed by an appropriate engine

We should not prematurely build our own workflow engine if Cloudflare Workflows satisfies the runtime requirements. That should be revisited in v6.

1. Cloudflare vs AWS — my recommendation

For Figentra, I would not choose one provider exclusively.

I'd use a hybrid architecture, but with a very clear rule:

Cloudflare at the edge; AWS for workloads that benefit from AWS-native infrastructure.

The reason is that Cloudflare is exceptionally attractive for the edge/control-plane layer, while AWS has a much broader backend infrastructure ecosystem and, importantly, very useful free-tier/credit economics for early workloads.

Cloudflare Workers Paid is currently $5/month/account and includes increased Workers/KV/Hyperdrive/Durable Objects allowances with no additional bandwidth/egress charge; Workers Free is also available with daily limits.

AWS currently offers new customers up to $200 in credits over six months, and individual services such as Lambda and SQS have substantial free allowances.

So I would architect Figentra like this:

4. AWS ECS vs Cloudflare Containers

This is more interesting.

Requirement	Cloudflare Container	AWS ECS/Fargate
Tiny/medium service	⭐⭐⭐⭐⭐	⭐⭐⭐
Scale to zero	⭐⭐⭐⭐⭐	⭐⭐
Simple deployment	⭐⭐⭐⭐⭐	⭐⭐⭐
Full Linux	⭐⭐⭐⭐⭐	⭐⭐⭐⭐⭐
Docker ecosystem	⭐⭐⭐⭐	⭐⭐⭐⭐⭐
AWS integration	⭐⭐	⭐⭐⭐⭐⭐
VPC/private networking	⭐⭐	⭐⭐⭐⭐⭐
Long-running workloads	⭐⭐⭐⭐	⭐⭐⭐⭐⭐
GPU	❌/limited	⭐⭐⭐⭐⭐
Enterprise AWS ecosystem	⭐⭐⭐	⭐⭐⭐⭐⭐
Operational simplicity	⭐⭐⭐⭐⭐	⭐⭐⭐
Early cost	⭐⭐⭐⭐⭐	⭐⭐⭐⭐

Cloudflare Containers charge based on active vCPU/memory/disk usage and can automatically sleep, which makes them particularly attractive for bursty services.

AWS ECS itself has no separate orchestration fee; you pay for Fargate/EC2 resources.

My choice

For Figentra's own services:

Default:
Cloudflare Worker

If full Node required:
Cloudflare Container

If AWS-specific / heavy / long-running:
AWS ECS/Fargate

Don't use ECS just because it is "enterprise."

5. SQS vs Cloudflare Queues
