# AI-agent governance — MAY vs MUST-escalate

Rules for what an AI agent (Kiro, Claude Code, Cursor, aider, ...) is allowed to
do autonomously in this workspace, and what requires a human sign-off BEFORE the
action lands.

Read alongside:

- [`AGENTS.md`](../../AGENTS.md) §Governance — the short-form summary this doc
  expands.
- [`commit-conventions.md`](commit-conventions.md) — the authoring layer for
  every commit an agent produces, including the provenance frontmatter every
  agent-authored document carries.
- [`priority-ordering.md`](priority-ordering.md) — the umbrella rule for
  resolving conflicts between overlapping guardrails.
- [`shell-commands.md`](shell-commands.md) — the sibling guardrail for
  tool-invoked shell.
- [`tmp-files.md`](tmp-files.md) — the sibling guardrail for scratch space.

## Precedence

1. This file wins over generic "AI can do X" guidance elsewhere in the repo.
2. When a specialised steering doc's rule contradicts a MAY line here, the
   specialised doc wins (e.g. `data-ownership.md` §"cross-service FK ban"
   prevails over MAY §"author code freely").
3. When any rule here contradicts a security guardrail (`shell-commands.md`,
   `tmp-files.md`, protected paths in `commit-conventions.md`), the security
   guardrail wins.
4. Every `MUST escalate` action is escalate-BEFORE-action. Never escalate-after.

## The two categories

Every agent action in the workspace lands in one of two buckets.

- **MAY** — the agent proceeds autonomously. No human sign-off, no confirmation
  prompt, no PR review gate at the action layer (a merge review still applies
  where the ambient repo policy requires one).
- **MUST escalate** — the agent MUST pause, surface the intended action to the
  human operator, and wait for an explicit confirmation. Silent execution is a
  governance breach.

"Escalate" means:

1. State the intended action in plain terms.
2. State the blast radius (what surfaces, what data, which repo, which branch).
3. State the reversal path (revert commit, restore backup, rollback deploy).
4. Ask for a Y/N. Wait for it.

## MAY — autonomous by default

Every action below is autonomous. The agent proceeds without asking.

### Authoring + refactoring

- Author new documentation under `.kiro/plans/`, `.kiro/reports/`, `.docs/adr/`
  (draft only — merging an ADR to `Accepted` status still requires a human).
- Author new steering docs under `.kiro/steering/` — but the doc is a DRAFT
  until a human reads + accepts it in a follow-up commit.
- Author new source files, tests, fixtures, migrations, seeders (draft — the
  agent tests locally; merging still gates on the repo's review policy).
- Refactor code within a single package or service so long as the public API
  contract does not change.
- Consolidate duplicate content (a `README.md` split across three folders → one
  canonical version + redirect stubs).
- Delete unambiguous fossils — files with zero references, dead workflow
  artefacts, orphaned build outputs. Deletion goes through git (recoverable via
  `git revert`), never `rm -rf` on tracked files.
- Update indexes + tables of contents when the underlying source changed.
- Rename symbols within a package when the name is code-searchable (use
  `semantic_rename` when available).

### Commits + branching

- Commit to a feature branch (never `main`) — one logical change per commit,
  message per [`commit-conventions.md`](commit-conventions.md) shape.
- Open a pull request / merge request against `main` with a descriptive
  summary + linked plan or ADR.
- Push a feature branch to `origin` (or the configured remote, typically
  `gitlab` for the workspace repo).
- Amend a not-yet-pushed commit to fix a message typo (once).
- Cherry-pick a commit into a feature branch when the source commit is clearly
  identified.

### Investigation + reporting

- Read any file the agent has access to.
- Run any read-only command — `git status`, `git log`, `pnpm ls`,
  `wrangler deployments list`, `terraform plan`, ...
- Run any dev-time command that operates on the workstation — `pnpm build`,
  `pnpm test`, `pnpm typecheck`, `pnpm lint`.
- Author audit reports under `.kiro/reports/` (name pattern:
  `YYYY-MM-DD-<slug>.md`).
- Author plans under `.kiro/plans/` (name pattern: `YYYY-MM-DD-<slug>.md`).
- Query MCP servers configured in `.mcp.json` (Doppler read-only, HeroUI docs,
  Sentry query, ...).

### Configuration + tooling

- Update package.json + lockfile refreshes for a NEW dependency
  the agent needed to install to complete a task.
- Update `catalog.json`, `package.json.exports`, `tsup.config.ts`,
  `vitest.config.ts` to keep the manifest set in sync with source changes.
- Update `.kiro/agents/`, `.kiro/steering/`, `.kiro/plans/`, `.kiro/reports/`
  indexes (`INDEX.md`, `ROUTING.md`) so the AI-agent surface stays truthful.
- Regenerate autogenerated content (terraform-docs, typedoc) between the
  literal markers those tools use.

## MUST escalate — human sign-off before action

Every action below MUST be surfaced to the human operator with the escalation
shape above BEFORE the agent proceeds. Silent execution is a governance breach
and reviewers reject any commit landing such an action without a recorded
escalation in the session transcript.

### Merges + main-branch writes

- Merge a pull / merge request to `main` in ANY repo (workspace or split).
- Force-push to `main` or any protected branch.
- Direct commits to `main` — even a "trivial" typo fix. `main` is human-gated.
- Rebase a shared branch — `git rebase` on `main` or a branch someone else is
  collaborating on.
- Delete a remote branch.
- Delete a git tag or move a git tag to a different commit.

### Production + shared-infrastructure changes

- Any production deploy — `wrangler deploy` to a prod Worker OR `terraform apply`
  against `terraform/envs/prd/`. Every prod deploy escalates.
- Any Terraform apply against staging or prod. `terraform plan` is MAY;
  `terraform apply` is MUST-escalate.
- Any DNS change (Cloudflare zone record, custom domain onboarding).
- Any TLS certificate change (Cloudflare edge cert, origin cert).

### Destructive operations

- Any mass delete — deleting more than 5 files at once OR any recursive delete
  (`rm -rf`, `git rm -r`, `find -delete`).
- Any database schema drop — `DROP TABLE`, `DROP DATABASE`, a migration rollback
  on shared data.
- Any data-truncating migration — `TRUNCATE`, mass `DELETE` without a narrow
  WHERE clause.
- Any Doppler config permanent-remove — soft delete is MAY when the config is
  clearly orphaned; permanent-remove is MUST-escalate.
- Any GitLab / GitHub project permanent-remove — 2-phase (soft delete +
  post-mark permanent-remove) MUST have the human confirm both phases.
- Any R2 bucket delete, Supabase project pause, or database instance stop.

### Secrets + auth

- Rotate any secret — Doppler tokens, GitLab tokens, Cloudflare API tokens,
  JWKS keys, database passwords, third-party API keys. Even when the rotation is
  per-schedule, the agent surfaces + waits before running the rotation command.
- Create or delete a service account, IAM role, or workload identity.
- Modify RBAC, grants, permissions, ScopeContext bindings, tenant-scoping rules
  that affect access control.
- Add a new MCP server that requires a token beyond the ones already documented
  in `AGENTS.md` §MCP.

### Cross-service contract changes

- Modify a cross-service contract — a per-service `api/openapi.yaml` OR a shared
  JSON schema — that existing consumers depend on.
- Modify a package's public API without a matching changeset (frontend) or a
  matching semver bump (backend).
- Modify an event catalogue (`<pkg>.events.ts` value + emit signature) in a way
  that changes wire format for existing consumers.
- Add or remove a database column that ships to production.

### Governance surface

- Modify this file (`ai-agent-governance.md`).
- Modify [`priority-ordering.md`](priority-ordering.md).
- Modify the "MUST escalate" list in [`AGENTS.md`](../../AGENTS.md).
- Change what agents can do — either by loosening a MUST-escalate rule OR by
  tightening a MAY rule. Both are governance changes.

## Escalation channels

The escalation shape depends on the surface the agent is running in.

- **Kiro / Claude Code interactive** — reply to the user in the chat with the
  four-part shape (intent + blast radius + reversal path + Y/N). Wait for an
  explicit "yes" reply. Never treat silence as consent.
- **CI-driven agent** — halt the workflow, post a comment on the PR / merge
  request naming the intended action, and require an approving review from a
  human maintainer before the pipeline resumes.
- **Terminal agent (aider, gh-copilot cli, ...)** — print the escalation block
  to STDOUT, prefix with `⚠ ESCALATION`, exit non-zero. The wrapping script must
  not auto-continue.

## Overrides + exemptions

Three escape hatches exist. Each is logged in the session transcript and
reviewed at commit-audit time.

- **`agents-may-override: <rule-id>` in the user's message.** The human operator
  has explicitly authorised the action within the CURRENT session scope. The
  override does NOT persist across sessions.
- **Break-glass label on a merge request.** A human sets the `break-glass` label
  AND names the reason in the MR description. The agent proceeds against the
  MUST-escalate rule the label identifies, then adds a note to the MR body
  documenting the override.
- **Per-repo exemption (§Per-repo agent-permission profiles).** Repos on the
  workspace-tooling side of the trust boundary carry a persistent exemption for
  a specific subset of MUST-escalate rules. See the profile table below.

Neither override waives the security guardrails
([`shell-commands.md`](shell-commands.md), [`tmp-files.md`](tmp-files.md),
protected paths in [`commit-conventions.md`](commit-conventions.md)). Those
rules stand under every override.

## Per-repo agent-permission profiles

Governance rules default to the strictest posture (assumes multi-human team

- production impact). For repos where that posture creates disproportionate
  friction — solo-operator workspace-tooling repos where main is not production
  and every write is reversible via git revert — a repo-specific profile relaxes
  named MUST-escalate rules.

The profile table:

| Repo                             | Trust class          | Relaxed rules                                                                  |
| -------------------------------- | -------------------- | ------------------------------------------------------------------------------ |
| `figentra-inc/workspace`         | Workspace-tooling    | Merges to `main` (FF-only, non-destructive) MAY proceed without per-session ok |
| `figentra-inc/backend/*`         | Service (production) | No relaxation — every MUST-escalate rule applies verbatim                      |
| `academorix/backend/*`           | Service (production) | No relaxation                                                                  |
| `academorix/*` (frontend/mobile) | Product (production) | No relaxation                                                                  |
| `stackra/backend`                | Framework            | No relaxation                                                                  |
| `stackra/frontend/*`             | Framework            | No relaxation                                                                  |

### Trust classes explained

- **Workspace-tooling** — repos that hold docs, plans, dev scripts, tooling
  configs, and IaC declarations. No runtime code that serves customer traffic.
  Blast radius on a bad merge = build/deploy tooling misbehaviour, reversible
  via `git revert`. Solo-operator ownership is the norm.

- **Service / Product / Framework** — repos that ship to production runtime or
  into consumers' installs. Blast radius on a bad merge = real user impact,
  potential outage, potential downstream package versioning drift. Multi-human
  review is the norm even for solo-owned repos.

### What the workspace-tooling relaxation covers

For `figentra-inc/workspace` specifically:

- **`git push gitlab <sha>:main` for a fast-forward** — MAY proceed. No force,
  no rewrites, no destructive ops. Every push must:
  - Be a strict fast-forward (rejected by `--ff-only` semantics if not).
  - Cite provenance in the commit body
    (`provenance: authored_by=<agent>; source=prompt://<slug>`).
  - Include an inline note in the push commit's summary IF it lands more than 5
    commits at once (audit-trail hygiene).
- **`git push gitlab <branch>` for feature branches** — MAY proceed as before.
  No change.
- **Force-push, rebase-of-shared-branch, tag-move, branch-delete on main** —
  still MUST-escalate. No relaxation on destructive ops.

For every OTHER repo (service, product, framework), the merge-to-main rule
applies verbatim.

### Adding a new repo to the workspace-tooling class

- The repo must have zero customer-facing runtime deploy path
- The repo must have zero package-publish-to-registry path (npm)
- The repo owner must be the solo operator (one active human writer)
- Add a row to the profile table above + reference the addition in the commit
  that lands the amendment

## Enforcement

Reviewers check the following at commit-audit time. Every finding is
review-blocking and requires the offending commit be reverted OR the escalation
be reconstructed after-the-fact with an operator sign-off in the PR description.

- Every commit landing a MUST-escalate action MUST cite the escalation in the
  commit body OR the associated PR description. Missing citation ⇒ finding.
- Every agent-authored document under `.kiro/plans/`, `.kiro/reports/`,
  `.docs/adr/` MUST carry the provenance frontmatter per
  [`commit-conventions.md`](commit-conventions.md) §Provenance.
- Every override-invoked action MUST be pair-signed — the human's authorisation
  quote + the agent's action + a matching `agents-may-override` or `break-glass`
  marker in the artefact.
- Every push to `main` MUST have originated from a human. Agent-authored commits
  to `main` are review-blocking, no exceptions.

## Anti-patterns

| Anti-pattern                                                                | Correct                                                                |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Agent auto-merges a "trivial" typo PR without asking                        | Escalate — every merge is human-gated per §MUST-escalate.              |
| Agent runs `terraform apply` against `terraform/envs/prd/` mid-session      | Escalate — every prod deploy is human-gated.                           |
| Agent `rm -rf` on a directory to "clean up"                                 | Escalate for anything > 5 files or recursive.                          |
| Agent rotates a Doppler token because a scheduled reminder fired            | Escalate — surface the reminder, ask, then run.                        |
| Agent adds an `.mcp.json` server pointing at a new remote                   | Escalate — new secret substrate touches the workstation trust surface. |
| Agent changes RBAC scopes or `@RequirePermission` guard values in bulk      | Escalate — access-control surface.                                     |
| Agent runs `git push --force-with-lease origin main`                        | Escalate — every force-push to a protected branch is human-gated.      |
| Agent silently rebases a shared feature branch                              | Escalate + coordinate with the other author.                           |
| Agent's response says "I'll deploy this to prod" then does it in one turn   | Never — split the response. State intent, wait, run.                   |
| Agent claims a MUST-escalate override without an `agents-may-override` line | Reject — override requires an explicit marker in the transcript.       |

## When you're tempted

- **"But it's a trivial change."** Trivial changes to `main` are still changes
  to `main`. Escalation on `main` is a one-line ask; the intermediate PR /
  feature-branch flow is the correct venue for "trivial".
- **"But the user just told me to fix the bug."** Fixing the bug on a feature
  branch is MAY. Merging the branch to `main` is MUST-escalate. The two steps
  happen separately.
- **"But the deployment is automated already."** Automation means the pipeline
  runs a `deploy` script when a human clicks "Approve" in the Actions UI. The
  click IS the human sign-off. The agent authors the PR that triggers the
  workflow; the human clicks Approve; the pipeline runs.
- **"But rotating the token is on the schedule."** The schedule is a reminder.
  Actual execution of the rotation is MUST-escalate every time.
