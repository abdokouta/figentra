# Files Service — implementation-complete plan

## Mission
Own file metadata and the secure lifecycle around object storage: upload sessions, downloads, access checks, checksums, versions, retention and asynchronous processing. Files does not own arbitrary application media semantics.

## Models
`File(id,tenantId,ownerRef,name,mimeType,size,checksum,status,objectKey,version,classification,createdAt)`; `FileVersion(id,fileId,version,size,checksum,objectKey,createdAt)`; `UploadSession(id,tenantId,fileId,expiresAt,parts,checksum,status,idempotencyKey)`; `AccessGrant(id,fileId,principalRef,permission,expiresAt)`; `ProcessingJob(id,fileId,processor,status,attempt,nextAttemptAt,resultRef)`.

## DTOs/interfaces
`CreateFileDto`, `InitiateUploadDto`, `CompleteUploadDto`, `DownloadRequestDto`, `GrantAccessDto`, `ProcessingJobDto`, `FileQueryDto`.
```ts
interface FileService { create(ctx,input):Promise<File>; initiateUpload(ctx,id):Promise<UploadSession>; completeUpload(ctx,id,input):Promise<File>; createDownload(ctx,id):Promise<SignedDownload>; delete(ctx,id):Promise<void> }
interface ObjectStorage { put(input):Promise<ObjectReceipt>; multipartStart(...):Promise<UploadSessionRef>; multipartComplete(...):Promise<ObjectReceipt>; delete(ref):Promise<void>; signGet(ref,ttl):Promise<string> }
```

## API
`POST /v1/files`; `POST /v1/files/:id/uploads`; `POST /v1/files/:id/uploads/:session/complete`; `GET /v1/files/:id`; `POST /v1/files/:id/download`; `DELETE /v1/files/:id`; `POST /v1/files/:id/access`; `GET /v1/processing/:id`.

## Security/interactions
Identity establishes principal; IAM authorizes file creation/read/write/delete and access grants. Tenant context determines object namespace. Signed URLs are short-lived and scoped. Provider credentials are secret references. Malware/media processors run as bounded workers and never receive unrelated tenant data.

## Object layout
Keys are generated by service (`tenantId/fileId/version/random`) and are never derived directly from user filenames. Metadata stores provider, bucket/container, key, checksum and version. Files supports real object storage through an explicit adapter; in-memory/local disk is development/test only.

## Upload correctness
Initiation creates durable session state. Completion verifies object existence, expected size and checksum before marking the file available. Abandoned sessions expire. Multipart completion is idempotent by session ID. A provider failure leaves an explicit recoverable state.

## Persistence
PostgreSQL tables `files`, `file_versions`, `upload_sessions`, `access_grants`, `processing_jobs`, `outbox`. Unique `(tenant_id,file_id,version)` and checksum metadata. Object storage is the binary source of truth; database stores metadata/references.

## Workers/scheduler
Consumer reacts to processing commands; worker performs antivirus/transcoding/metadata extraction and orphan reconciliation; scheduler expires sessions, retention candidates and stale jobs. Retries are bounded with DLQ/quarantine.

## Observability
Upload/download/processing latency, bytes, provider errors, checksum failures, orphan count, job lag and signed URL issuance. Never log object contents or signed URLs.

## Testing
Object-provider conformance, multipart retries, checksum mismatch, access authorization, tenant isolation, expiry, concurrent completion, processing failure/retry, orphan reconciliation, retention and migration tests.

## Completion gate
Real production object storage is selected and configured; binary data never enters PostgreSQL; every access is IAM-authorized; upload completion is checksum-verified and idempotent; no fake production filesystem driver remains.
