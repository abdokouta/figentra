# `@stackra/i18n` — implementation plan

## Purpose
Canonical localization boundary for messages, locale negotiation, pluralization, number/date/currency formatting, locale metadata and RTL direction across web, native and desktop runtimes. Product content/catalog ownership remains in applications/services.

## Public API
```ts
interface I18nService {
  locale():Locale;
  setLocale(locale:Locale):Promise<void>;
  t(key:MessageKey,values?:Record<string,unknown>,options?:TranslateOptions):string;
  has(key:MessageKey,locale?:Locale):boolean;
  formatNumber(value:number,options?:Intl.NumberFormatOptions):string;
  formatDate(value:Date|number|string,options?:Intl.DateTimeFormatOptions):string;
  formatCurrency(amountMinor:number,currency:string,options?:CurrencyFormatOptions):string;
  direction(locale?:Locale):'ltr'|'rtl';
}
interface MessageCatalog { locale:Locale; version:string; messages:Record<string,string>; }
```

## Locale model
Locale identifiers are normalized/canonicalized (for example BCP-47 style tags). Supported locales are explicitly registered. Fallback is deterministic: exact locale → language parent → configured default locale → missing-key strategy. Unsupported locale never silently changes to a user-controlled arbitrary catalog.

## Message contracts
Catalogs are versioned, schema-validated and immutable once published. Message values are text/templates, not executable code. Variables have declared types/requiredness. Missing/extra variables produce development diagnostics and deterministic runtime fallback; they never execute arbitrary expressions.

## Loading
Static catalogs are bundled explicitly. Dynamic catalogs are loaded through an allowlisted source with size/deadline limits and cache/version validation. A failed optional locale load falls back to the last valid catalog/default locale according to policy; security-critical application labels must be bundled.

## Formatting
Use `Intl` or runtime-equivalent locale-aware formatters. Currency amounts are converted from minor units by explicit currency metadata. Date/time formatting must respect locale and timezone options supplied by the caller; it never guesses business timezone. ICU/plural categories are normalized across supported runtimes.

## RTL
Locale metadata provides `direction`, script and formatting conventions. Components consume direction from I18n/Theming; i18n does not manipulate DOM styles itself.

## Security/performance
Catalogs cannot contain executable JS or arbitrary HTML. Unsafe interpolation is escaped by the rendering layer. Catalog size, nesting and key count are bounded. Compiled message functions are cached immutably by `(locale,catalogVersion,key)`.

## Observability
Measure locale resolution failures, missing keys, catalog load latency/failures and formatter errors. Never log translated message payloads that may contain PII. Production missing-key rate is monitored through aggregate metrics.

## Testing
Fallback matrix, locale normalization, plural rules, formatting snapshots, RTL metadata, catalog schema validation, missing/extra variables, dynamic-loader failure and cache behavior. Conformance runs Node/browser/native where supported to detect Intl differences.

## Implementation phases
1. Locale/catalog contracts and normalization.
2. Translator/pluralization and deterministic fallback.
3. Number/date/currency formatters.
4. Static/dynamic loaders and runtime adapters.
5. React bindings, testing, security/performance verification.

## Exit criteria
- One localization contract is used across apps.
- Catalogs are versioned, validated and non-executable.
- Fallback and RTL semantics are deterministic.
- Locale-sensitive formatting is covered by cross-runtime tests.
- No product service owns a second translation engine.
