# `@stackra/cache` — implementation plan

## Purpose and boundary
Ephemeral acceleration and coordination state. Cache is never authoritative durable storage, event history or database replacement. Every cached value must have a source of truth and bounded TTL/invalidation semantics.

## Public API
```ts
interface CacheStore<V=unknown> {
  get<T extends V>(key:string):Promise<T|null>;
  set<T extends V>(key:string,value:T,options?:CacheSetOptions):Promise<void>;
  delete(key:string):Promise<boolean>;
  exists(key:string):Promise<boolean>;
}
interface CacheManager extends CacheStore {
  wrap<T>(key:string,loader:()=>Promise<T>,options?:WrapOptions):Promise<T>;
  invalidate(key:string):Promise<void>;
  invalidatePattern(pattern:string):Promise<number>;
}
```

Required options: TTL, namespace, stale-while-revalidate (when supported), serialization version, size limit and optional distributed-lock policy.

## Provider model
Redis is the production distributed cache adapter. In-memory cache is test/development only and must be explicitly configured. Drivers expose capabilities: TTL, atomic compare-and-set, distributed locks, tag invalidation and pattern invalidation. Consumers cannot assume an unsupported capability.

## Key model
Keys are generated by helpers such as `generateKey`, `generateListKey`, `generateViewKey` and canonical request hashing. Tenant-scoped values include environment/service/tenant namespace. Keys do not include tokens, passwords or raw PII. Every key family has an owner, version and invalidation event.

## Stampede protection
`wrap` performs process-local single-flight and may acquire a bounded distributed lock when supported. Lock TTL, wait timeout and stale-while-revalidate policy are explicit. A lock failure must not create an infinite wait. Lock loss never writes an unowned result unless the driver supports fencing/versioning.

## Invalidation
Database writes commit before outbox publication. Cache invalidation occurs after commit based on domain events. Tags/namespaces are preferred to broad pattern scans. Pattern invalidation requires an explicit capability and bounded key-space behavior.

## Reliability
Cache get/set have strict connect/operation timeouts and bounded transient retries. If cache is unavailable and the source of truth can safely answer, the application continues with a miss. Cache must never be a mandatory correctness dependency unless an explicit service contract says the operation is optional.

## Security/tenancy
Namespace isolation is mandatory. Serialization rejects unsupported types and enforces maximum item size. Sensitive payloads require explicit classification and encryption policy. Operational diagnostics exclude cached secrets.

## Observability
Metrics: hit/miss, latency, value size, invalidation count, stampede waits, lock contention, eviction and provider errors. OTel spans identify cache operation/key hash rather than raw key/value.

## Testing
Driver conformance for expiry, atomicity, locks, invalidation, serialization and outage behavior. Tests simulate concurrent `wrap`, lock expiry/loss and tenant-key collisions. Integration tests run against real Redis for production parity.

## Implementation phases
1. Core interfaces/key/serialization model.
2. Redis/in-memory drivers.
3. wrap/single-flight/distributed lock semantics.
4. invalidation/tag/versioning.
5. runtime adapters/observability/security.
6. conformance/load/outage tests and release.

## Exit criteria
- Production cache uses a real distributed adapter.
- Every key family has owner/version/TTL/invalidation semantics.
- Cache failure degrades to source-of-truth reads where safe.
- No arbitrary Redis access exists outside the adapter.
- No authoritative business state is stored in cache.
