# API Gateway — Architecture Contract

## 1. Decision

The Figentra API Gateway is an **independent Cloudflare Worker implemented with Hono**. It is the public edge boundary for browser, mobile, server-to-server and approved webhook traffic entering Figentra.

It is **not** a NestJS application and must not be converted into one without an ADR proving that losing Cloudflare edge placement, Worker bindings, edge WAF/routing and low-latency global ingress is preferable.

NestJS remains the canonical runtime for the 14 business/domain services. Cloudflare Worker + Hono is the canonical runtime for Gateway, Registry and Infrastructure Orchestrator because these are independent edge/control-plane runtimes.

## 2. Why Cloudflare Worker + Hono

The Gateway's workload is edge-native and stateless: host resolution, transport normalization, JWT prevalidation, request identity propagation, WAF/rate-limit integration, Registry-backed route lookup, Service Binding/authenticated HTTPS forwarding, response normalization, edge cache decisions and realtime/stream proxying.

A full NestJS gateway would add container/runtime cost and latency while duplicating Cloudflare's public edge functions. Business services already provide NestJS lifecycle, validation, domain authorization and persistence. Therefore NestJS at the Gateway would create a second application framework at the wrong boundary.

## 3. Ownership

Gateway owns:
- public DNS/host/application resolution;
- public route discovery and routing;
- edge request normalization;
- canonical request ID creation/validation and propagation;
- correlation/causation/trace-context propagation;
- client IP/proxy metadata normalization from trusted Cloudflare context;
- public CORS and security-response-header policy;
- WAF/bot/abuse integration;
- coarse/edge rate limiting and traffic shaping;
- JWT/access-token structural and cryptographic prevalidation where configured;
- public client/service credential extraction and safe forwarding of verified context hints;
- upstream selection: Worker Service Binding or authenticated HTTPS service origin;
- origin authentication and origin shielding;
- safe retries/timeouts/circuit protection at the transport boundary;
- edge-safe response caching;
- WebSocket/SSE/streaming proxy semantics;
- upload/download transport limits and direct-upload handoff patterns;
- normalized edge transport errors;
- edge access logging, metrics and tracing;
- Registry metadata consumption/caching;
- gateway health/version/build metadata.

## 4. Explicit non-ownership

Gateway does not own:
- business/domain entities or persistence;
- final authentication/session truth;
- final IAM authorization;
- tenant membership truth;
- commercial entitlement decisions;
- service DTO/domain validation beyond transport/routing safety;
- service transactions;
- domain workflows;
- service queues/jobs/schedulers;
- business notifications;
- audit evidence source of truth;
- arbitrary response shaping that changes domain semantics;
- source-service error semantics beyond safe transport normalization;
- another service's database, cache or provider credentials.

## 5. Trust model

```text
Internet client
  -> Cloudflare DNS/WAF/TLS
  -> API Gateway Worker
     -> normalize public transport
     -> establish request/correlation/trace IDs
     -> route/app resolution
     -> token prevalidation / public abuse controls
     -> signed internal gateway context
     -> authenticated upstream transport
  -> NestJS service
     -> validate gateway/service identity context
     -> authoritative Identity/PrincipalContext
     -> authoritative Tenant context
     -> authoritative IAM/commercial checks
     -> DTO/domain validation
     -> use case / transaction
```

The Gateway improves security and rejects obviously invalid traffic early, but a compromised/misconfigured edge must not be sufficient to bypass service security. Services remain security boundaries.

## 6. Context contract

Gateway may propagate trusted, integrity-protected internal metadata: request ID, correlation ID, traceparent/tracestate, resolved application/environment, normalized route ID, client/network classification, and verified-token summary where allowed. It must never forward a client-supplied `principalId`, `tenantId`, role, permission or authorization decision as trusted merely because it appeared in a header/body.

Any internal context header generated by Gateway is stripped from public input first and reissued by Gateway. Service-to-service context uses the platform signed/integrity-protected context contract.

## 7. Routing architecture

Route ownership comes from Application Registry projections produced by the owning NestJS services and independent Workers. Gateway holds a bounded, versioned edge cache of safe routing metadata. Registry is metadata/control plane; services remain application truth.

Route lookup key includes host/application/environment + HTTP method + normalized path template/version. Route metadata declares upstream, auth mode, body limit, timeout class, cache policy, rate-limit policy, streaming mode, webhook mode and required edge capabilities.

## 8. Availability model

Gateway must remain stateless per request. Safe routing metadata can be cached in Worker memory/KV/Cache API according to policy. No business transaction depends on Gateway durable storage.

If Registry is temporarily unavailable, Gateway may continue using a last-known-good, unexpired/signed route snapshot within its configured safety window. Unknown routes fail closed. It must not dynamically guess service origins.

## 9. Service transport

Preferred order:
1. Cloudflare Service Binding for Worker-to-Worker upstreams.
2. Authenticated HTTPS to private/protected NestJS origins for container services.

Origin HTTPS requires strict host allowlist, TLS validation, service authentication, no open proxy behavior, timeout policy and origin address secrecy.

## 10. Security posture

- TLS terminates at Cloudflare edge; upstream TLS remains mandatory where HTTPS is used.
- WAF/bot/rate controls are edge-global controls, not replacements for service authz/validation.
- JWT prevalidation rejects invalid issuer/audience/signature/expiry where Gateway has configured validation metadata.
- Gateway does not own session revocation truth; service/Identity may reject a token that Gateway accepted structurally.
- No user-controlled URL selects an upstream.
- No arbitrary header forwarding.
- Hop-by-hop and internal headers are stripped.
- Request smuggling ambiguities are normalized/rejected.
- Content length/type/encoding limits are enforced.
- CORS is application/route metadata-driven.

## 11. Multi-tenancy

Host/application resolution is authoritative only for application routing, not tenant authorization. Tenant hints from host/path/token may be forwarded as untrusted/requested context, while the service resolves and authorizes the actual tenant context.

## 12. Observability split

Gateway owns edge access/transport observability. Services own domain/application observability. A request therefore commonly generates one Gateway server span plus downstream service server/client/internal spans with the same trace/request/correlation IDs. Duplicate semantic logging is avoided by assigning different responsibilities, not by removing service logs entirely.

## 13. Architecture acceptance

Accepted only when Gateway is CF Worker + Hono; public edge controls are centralized; service boundaries remain authoritative; routing is Registry-driven and allowlisted; internal context cannot be forged by clients; retries/caching are safe; realtime/file transport is explicit; and no business/domain logic migrates into the edge.
